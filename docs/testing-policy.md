# Brk 测试规矩

给所有写代码、做验证的任务看，包括父任务派出去的子任务。子任务的说明会直接指向这份文档。

## 为什么有这份规矩

现状：到 2026-11-10，仓库里有 1,726 个单元测试、397 个默认登记的原生场景，`verify/` 下堆了 29,188 个运行记录文件（约 9.5 GB），每次合并要跑整套单测、五十多个原生场景、真实 agent 和整套截图对比。用户的原话是测试用例太多了，完全没必要。

推理：这么多测试并没有多防住什么。2026-11-05 的双指滑动认不出、红黄绿按钮悬停闪跳、Toast 位置不对，2026-11-07 的 Max 功能完全用不了，还有快捷键失灵，出事时相关场景全部通过。原因是那些检查在进程内注入事件、绕过了用户真正点的按钮，或者等画面稳定后才去读。数量多只带来两个结果：每次合并跑很久；真正的失败淹没在不稳定的失败里，大家习惯了重跑。

结论：当天把单元测试删到 984 个、默认原生场景删到 102 个，`verify/` 整个删掉（删减清单和理由在 `docs/testing-inventory.md`）。下面几条规矩是为了不再长回去。

## 什么样的测试值得写

现状：删掉的测试大多属于这几类：把常量、像素、颜色、文案重抄一遍；浅色深色、每个 agent、每种 Profile 各抄一份；换个入口把同一条规则再测一遍；为某次合并写的一次性证据场景；只拍图的 Look 场景。

推理：一条测试的价值在于它能发现一个用户会注意到的问题，而且别的测试发现不了。外观的问题 station（`scripts/station/` 里的同屏截图对比：同一块屏上截 Brk 的画面，和真 Arc 1.170 的参照图逐像素比）能看到，单元测试再抄一遍数字只会在改数字时多改一处。真实使用里坏掉的问题，进程内的检查发现不了，只有走真实键盘、鼠标、触控板的原生场景能发现，但这种场景慢，所以只给主要流程用。

结论，一条测试要同时满足两条才写、才留：

1. 它坏了用户会注意到（行为错、丢数据、隐私或安全泄露、崩溃），或者它守的是一条以前坏过一次的规则；
2. 没有别的测试已经能发现同一个问题。

每次改动加多少：

- **修 bug**：加一个能复现这个 bug 的测试，修好后它通过。能用单元测试就用单元测试。只有 bug 出在真实输入、窗口、Chromium 嵌入这一层、单元测试碰不到时，才加原生场景，而且必须用真实输入（`PhysicalKeys`、`PhysicalPointer`、真实滑动），不能用控制通道在进程内派发。
- **新功能**：每条用户看得到的规则一个单元测试，一个功能一般 3 到 5 个，最多 10 个。原生场景最多 1 个，从用户真正用的入口走（真实键盘鼠标点按钮、菜单），并登记进 `scripts/native-sets.txt` 的一个组；没登记的场景门不会跑。
- **不写**：只核对常量、像素、颜色、字号、文案的测试；浅色深色各一份、每个 agent 各一份（除非测的正是那个 agent 自己的协议）；换个入口再测一遍；为合并或审查补的证据场景；只拍图的 Look 场景；依赖外网的场景。
- **删**：一条规则改掉了，它的测试跟着改或删。发现两条测试防的是同一个问题，删一条。删单元测试的理由如果是"原生场景已经覆盖"，那个场景必须真的在 `scripts/native-sets.txt` 里；反过来也一样，两边只能留一个时留单元测试，因为它便宜。

上限：smoke 组（每次合并都跑的那几个真实输入主流程场景）不超过 10 个场景；其余每个组不超过 16 个；组满了，新场景要换掉一个旧的。整套单元测试的运行时间不超过 150 秒（现在约 120 秒，不含编译），单个单元测试超过 2 秒要在注释里说明为什么。

## 测试记录不进仓库

现状：以前每个任务都把截图、日志、运行报告、补丁、manifest 提交进 `verify/<任务>/`，一次合并留下几百上千个文件。台账 `docs/completion/features.json` 的证据字段指向这些文件。2026-11-10 用户决定 `verify/` 全部删掉，当天又把它从整个 git 历史里清掉了（为了推到 GitHub 并准备公开仓库），所以这些旧记录已经取不回来，提交号也都变了。

推理：这些记录在合并当时有用，合并以后几乎没人再看。它们留在最新的树里，只会让仓库越来越大、让 grep 和代码审查越来越慢。

结论：

- 测试记录（图片、日志、运行报告、录屏、补丁、manifest）一律不提交。它们放在仓库外，按任务分文件夹：`~/brk-evidence/<任务>/`。`scripts/run-native.py` 默认就写到 `~/brk-evidence/native/<名字>/`。
- 交给父任务看的文件夹里只放：一份 `README.md`（查了什么、怎么查的、结果和数字）、一份运行报告、最多 5 张图。图只拍有争议或者用户要看的画面。
- 分支里只提交代码、测试，需要时再加一份不超过一页的说明 `docs/checks/<日期>-<任务>.md`：查了什么、用的命令、结果和数字，不放图片和日志。没有必要就不写，写在提交说明里也可以。
- 台账某一行要标 verified，证据字段写 `docs/checks/` 下那份说明，或者写 `<提交号>:<路径>`（历史里的文件）。`scripts/check-completion.py` 会核对这两种写法。
- 代码注释和旧文档里还有很多 `<提交号>:verify/...` 的写法，那是 `verify/` 删除前的位置，复制到 `git show` 后面就能看到原文件。

## 合并门

现状：之前一次合并门（AI 第 8 步）跑整套单测，本机运行 227 秒，加上编译；53 个夹具 AI 场景 613 秒；5 个真实 Claude 场景 365 秒；station 在分支和 main 上各跑一遍全部画面。每个分片还各自跑一遍同样的东西。

推理：大部分改动只碰一块代码。整套原生场景里，和这块代码有关的只是一小部分；和这次改动无关的场景跑一百遍也只是在重复上一次的结果。真正需要每次都跑的，是几条用真实输入走主要流程的场景，因为那几条坏了用户第一时间就会发现，而它们会被很多地方的改动弄坏。

结论，合并前跑这些，不多跑：

1. **单元测试全跑**：`python3 scripts/with-batch-locks.py --lock /tmp/brk-batch-build.lock -- swift test`。
2. **smoke 每次都跑**，再加上改到的那几块对应的组：`python3 scripts/run-native.py <新名字> --set smoke,<组>`。这个脚本自己拿原生锁，不要再套一层锁；它会核对报告里有没有漏跑的编号。改了哪里跑哪个组：

| 改到的代码 | 加跑的组 |
| --- | --- |
| `Sources/BrkSidebar`、`Sources/BrkContent`、`Sources/BrkLayout` | sidebar；动到 Space 的再加 spaces |
| `Sources/BrkOverlays` | commandbar；Space 对话框加 spaces |
| `Sources/BrkLibrary` | library、downloads |
| `Sources/BrkSettings` | profiles、windows |
| `Sources/BrkTheme` | spaces |
| `Sources/BrkCEF`、`Sources/BrkEngine` | core、pages、downloads、sites、find |
| `Sources/BrkApp` 里的按键路由和菜单 | keys |
| `Sources/BrkApp` 里的窗口、Little Arc、Peek、退出 | windows |
| `Sources/BrkApp` 里的存档和恢复 | core |
| `Sources/BrkApp/Agents`、`Sources/BrkLocalModels`、AI 相关的状态规则 | ai |
| `Sources/BrkDomain` | 规则所属功能的组，再加 core |
| `engine/`、`Sources/BrkCoreEngine` | 在 Brk 自己的 Chromium 上跑：`engine/run-native-core.py <新名字> --set smoke,sites` |
| 新加了画面、按钮或界面文字（任何模块） | 再加 `--only TextLayout`：它在所有主要画面上找被截断的文字。2026-11-10 它发现 Library 的 AI 对话页有 4 处文字被截断，那一页是 AI 第 7、8 步加的，当时的门没跑它 |
| 只改了测试、文档、脚本 | 只跑单测 |

3. **station 只在看得见的东西变了时跑**，只跑相关画面，分支和 main 在同一块屏上各跑一次比较：`~/.t3/projects/brk/scripts/station/station.sh <分支> ~/brk-evidence/<任务>/station-branch <画面>`，再用 main 跑一次。真 Arc 的参照图在 `~/brk-arc-reference/`，夹具网站在 `scripts/station/fixture-site/`，要在 8764 端口开着：`python3 -m http.server 8764 --bind 127.0.0.1 --directory scripts/station/fixture-site`（在主 checkout 里运行）。
4. **真实 agent 只在 agent 相关代码改了时跑**，一次只跑和改动有关的一个入口，因为每次都花用户的额度：`python3 scripts/run-native.py <新名字> --set real --agent claude` 会跑全部四个；只跑一个用 `--only AIRealUI-claude`（Max 的各个功能）、`AIRealUIBasic-claude`（小模型）、`AIRealRightPanel-claude`（右侧面板对话）或 `AIRealLocal-none`（只用本地模型）。
5. **失败了先单独重跑一次**，用新名字只跑失败的编号。第二次还失败就是真的失败，要修或者说明，不能靠反复重跑凑出通过。

时间（本机 Mac mini M1 实测，2026-11-10，和其他任务的编译、截图同时进行，秒数有出入）：

| | 删减前 | 删减后 |
| --- | --- | --- |
| 单元测试运行（不含编译） | 1,726 个，227 秒 | 984 个，121 秒 |
| 每次必跑的原生场景 | 没有固定集合；上次门跑了 53 个 AI 场景，613 秒 | smoke 8 个，90 秒 |
| 全部默认原生场景 | 397 个，约 52 分钟（历史中位数之和，10 月 31 日后没人跑全过） | 102 个，一次跑完 1,173 秒（约 20 分钟） |
| 一次 AI 改动的门 | 单测 227 秒 + 53 个夹具 AI 场景 613 秒 + 5 个真实 Claude 场景 365 秒，约 20 分钟，再加两遍 station 全部画面 | 单测 121 秒 + smoke 90 秒 + ai 组 236 秒 + 一个真实入口（例如 AIRealRightPanel 约 40 秒），约 8 分钟；station 只在看得见的东西变了时跑相关画面 |

删减后第一次把 102 个场景全跑完时，94 个通过、7 个失败、1 个按设计跳过（Core-popup 只在 Brk 自己的引擎上跑）。6 个用真实鼠标的拖拽场景失败时 Brk 的窗口不是当前窗口（共用的屏幕上别的应用被切到了前面），单独重跑全部通过。TextLayout 两次都失败，它发现的是 main 上真实存在的问题：Library 的 AI 对话页有 4 处文字被截断（搜索框的占位文字、三个筛选按钮的文字），要在产品代码里修。
