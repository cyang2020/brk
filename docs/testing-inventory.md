# 测试清点与删减清单（2026-11-10）

## 背景

2026-11-10 用户说测试用例太多，大部分完全没必要。当时 main 在 75d4fe4a（933155f6 只多了一份命令栏排序的研究），规模是：

- 单元测试 1,726 个，分布在 `Tests/` 下 201 个文件里；
- 原生端到端场景 85 个文件、26,560 行，默认登记 397 个场景，另有 9 类要设环境变量才跑的真实 agent 场景；
- `933155f61c:verify/` 下 29,188 个受 git 管的文件，其中 8,227 张图片，约 9.5 GB；
- 合并门要跑整套单测、53 个以上的原生场景、真实 agent 和与 main 的同屏截图对比（station）。

这份文档记录删减前的清点结果和删减清单：每组测试有多少、跑多久、实际防的是什么问题，留哪些、删哪些、为什么。数字的来源如下：

- 单元测试的个数和耗时在这台 Mac mini（M1）上实测，命令是 `swift test --skip-build`，删前删后各跑一次；
- 原生场景的耗时取 `933155f61c:verify/` 里 555 份历史运行报告中每个场景通过时的耗时中位数。最近一次把所有场景跑完是 10 月 31 日（187 个场景，20 分钟），之后场景翻了一倍多，再没人全跑过；
- "以前坏过"来自 git log 里的修复提交、记忆笔记里记下的用户报告，以及历史报告里的失败记录。

## 留下一条测试的规则

先看这个仓库里几次真实发生的问题。2026-11-05 用户报告双指滑动切 Space 几乎认不出、红黄绿按钮悬停时闪跳、Toast 位置不对，相关场景当时全部通过：滑动场景是在进程内把滚动事件直接塞给窗口，真实的触控板事件先被标签列表的滚动视图拿走了；按钮场景在指针到位半秒后才读位置，闪跳只有一帧。2026-11-07 用户说 Max 的功能完全用不了，派发式的 AI 场景全过，因为它们绕过了按钮，而新用户没有固定标签时根本看不到 Tidy 按钮。快捷键也出过同样的事。

从这些事推出两点。第一，在进程内注入事件、或者事后再读状态的检查，会在真实使用坏掉时照样通过；几条用真实键盘、鼠标、触控板走主要流程的检查，比一大堆进程内检查有用。第二，大量测试并没有多防住什么，反而让每次合并要跑很久、让真正的失败淹没在不稳定的失败里。

所以一条测试只有同时满足下面两条才留：

1. 它坏了用户会注意到（行为错、丢数据、隐私或安全泄露、崩溃），或者它守的是一条以前坏过一次的规则；
2. 没有别的测试已经能发现同一个问题。

照这两条，通常要删的是：重复和换个入口再测一遍的；只把一个常量、像素数、颜色、字号、文案重抄一遍的；行为测试已经覆盖到的管道测试（单个字段的编码、"命令接上了"、"设置存下了"）；浅色深色、每个 agent、每种 Profile 各抄一份但行为跟这个变体无关的；为某次合并或审查写的一次性证据场景；不稳定又没有独到之处的。

在执行中又补了四条：

- 单元测试和原生场景不能互相指望着一起删。删一条单元测试的理由是"原生场景已经覆盖"，那这个原生场景就必须留下，反过来也一样。第一轮删完后核对发现，UI 组有 35 条单元测试是靠后来被删的原生场景兜底的，已经恢复成每条规则一个单元测试。单元测试便宜，所以两边只能留一个时留单元测试。
- 已知失败、长期没人修的场景删掉，缺口写在台账那一行的 remaining 里。每次门里都红着的场景只会让人习惯忽略失败。
- 依赖外网的场景删掉，它的失败说明不了 Brk 的问题。
- 真实 agent 场景会花用户的额度，默认不跑；每个入口只留一个，只在 agent 相关代码改了时跑。

删掉的主要是这几类，每类举几个例子：

- 重抄常量和像素数：侧栏重置宽度等于四个 Favorites 宽、红黄绿按钮中线、各卡片的尺寸和圆角、迷你播放器每张卡的大小。这些画面 station 拿真 Arc 的截图对比时会看到，单元测试再抄一遍数字防不住什么，只会在改数字时多改一处。
- 重抄颜色和文案：Toast 的措辞（ToastCatalogTests 从 17 个剩 2 个）、主题的亮度和颜色值（PolicySpecTests 从 31 个剩 15 个）、各菜单的标题列表。整个菜单栏和 Arc 菜单文件的逐项比对留了一个，因为它是唯一检查全部快捷键的地方。
- 换个入口再测一遍：拖拽和菜单"固定"走的是同一个状态规则，留一个；分屏"拆出一个"和"全部拆出"留覆盖面大的那个。
- 管道和测试工具自测：测试时钟、控制通道的上下文菜单捕获、文字截断检查器的 20 个自测（真实应用上的 TextLayout 场景会跑这个检查器）。
- 审查时补的证据测试，跟已有行为测试重复的部分。
- 一个 40 秒的归档上限测试（ReduceSpecTests 里，单个测试占了整套的六分之一时间），上限规则另有测试覆盖。

main 上原有一个失败的测试：它要求每个命令都在别处有行为测试，并写死了命令总数。删减后这个前提不再成立，它改成了"每个命令和事件送进状态机都不崩"，写死的计数去掉了。

留下的主要是：用户能看到的状态规则；存档、恢复和迁移（丢数据的风险）；隐私和隔离（无痕窗口、Profile、cookie、页面注入检查、API key 不进存档文件）；有真实边界情况的解析和排序，每条规则一个；以及名字或注释里写明修过的 bug、用户报告、审查发现的缺陷。

### 删掉的，按原因
